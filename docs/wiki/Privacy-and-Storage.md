# Privacy and Storage

Career Evidence Toolkit keeps the public plugin repository separate from the user's private career data.

## What belongs in the repository

The public repository should contain reusable project assets such as:

- skill instructions;
- blank or sanitized templates;
- validation scripts;
- documentation;
- examples that do not expose real personal data.

## What must stay private

Do not commit real user career data to the public repository, including:

- resumes and CVs;
- personal contact information;
- certificate files;
- profile photographs;
- private professional-profile exports;
- application records;
- generated role-specific resumes;
- private storage URLs or account identifiers.

## Private career workspace

Onboarding requires one durable private storage location. The exact provider is flexible as long as the agent can use it and the user understands the access being requested.

Examples include a local folder, Google Drive, ChatGPT Library, Dropbox, or another supported private storage system.

## Permission boundaries

Read access does not automatically authorize writes. External actions such as uploads, edits, renames, repository changes, or public sharing should be explicit and appropriate to the user's request.

## Secrets

The toolkit does not need passwords, API keys, access tokens, recovery codes, or similar secrets.

Within this project, the word **credentials** refers to professional certificates and public credential records.

## Template sanitization

If a user supplies a custom `.docx` resume template, the original should remain unchanged. The adopted template should be a sanitized clone where personal text is replaced with placeholders and document metadata is removed before the template is reused.

## Public profiles

Public professional profiles can be useful evidence sources, but they should be treated as sources to read—not as permission to edit those profiles or republish their contents elsewhere.
